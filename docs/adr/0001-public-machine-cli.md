# Use `moss machine` as the public, plan-driven machine interface

The public CLI is `moss machine plan`, `moss machine apply` and `moss machine bootstrap`. The operator declares machine source and policy once in a private off-host configuration; `plan` observes the known target, builds/evaluates the candidate and writes a versioned, typed proposal (`install` or `update`). `apply` accepts only a recognized plan type and rechecks the target, configuration, selector, branch tip and operation-specific conditions before changing state. An install also requires an explicit whole disk and typed erase confirmation. Applying an update never runs Disko. `bootstrap` is separate because installation changes the SSH host-key trust boundary.

The implementation lives under `packages/cli/`: editable command and machine source in `src/`, with standalone generated executables in `bin/`. The unrelated GitHub App audit is a separate package under `packages/github-app-audit/`. There is no `toolkit/` tree or public `moss toolkit` / `moss deploy` / `moss provision` interface. Target-side scheduled polling and reviewed selector/branch transitions remain internal. An operator update plan can only follow an already selected, non-divergent branch; it must not silently change the baseline. The public command tree and tests are implemented in [PR #15](https://github.com/benjaminpreiss/themoss.net/pull/15); the actual install/update and recovery behavior is documented in that PR's deployment runbook.

One plan model can describe different *effects* without granting arbitrary executable steps. A plan is neither authorization nor evidence of a completed change (the receipt serves the latter role). Missing evidence, changed tips, uncertain switch outcomes, a missing install receipt, or a different physical disk all require a stop rather than automatic destructive reconciliation.

This decision does **not** ship issue #1's proposed repair, backup, restore, VM or peer management features. A future web/proxy/VM flow must use signed, authorized, fresh, typed requests to a validating hypervisor management service; the proxy must not run CLI strings on the host or expose a host shell. Existing consumers pinned to older commits retain their original interface until they choose to migrate.
