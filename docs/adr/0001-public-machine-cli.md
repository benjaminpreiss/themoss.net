# Use `moss machine` as the public, plan-driven machine interface

The public CLI is `moss init`, `moss machine plan`, `moss machine apply` and `moss machine bootstrap`. The operator declares machine source and policy once in an operator-local, off-target configuration. `moss init` creates an operator-local `.moss/` in the current directory or Git ancestor and, when in Git, prints an ignore instruction if needed; it neither edits `.gitignore` nor generates a machine config. By default `plan` stores per-target configuration, immutable plans and the latest-plan symlink there. Every use of operator-local storage checks that an existing `.moss/` is ignored when in Git; all explicit operator file paths are checked as well. No private file is committed, and explicit path overrides remain available for automation. On first use, `plan` asks for those choices and creates the configuration if it does not exist. For a new installation it probes whole disks read-only, proposes the only disk when unambiguous, or requires the operator to choose one from a numbered list. It records that candidate in the configuration, builds/evaluates the known target and writes a versioned, typed proposal (`install` or `update`). `apply` selects the latest successfully written plan for a target (or an explicit path), never the newest plan across multiple targets; it accepts only a recognized plan type and rechecks the target, configuration, selector, branch tip and operation-specific conditions before changing state. Disk auto-selection is only a proposal, never erase authorization: an install still re-probes the selected whole disk and requires typed disk-specific confirmation. Applying an update never runs Disko. `bootstrap` is separate because installation changes the SSH host-key trust boundary.

The implementation lives under `packages/cli/`: editable command and machine source in `src/`, with standalone generated executables in `bin/`. The unrelated GitHub App audit is a separate package under `packages/github-app-audit/`. There is no `toolkit/` tree or public `moss toolkit` / `moss deploy` / `moss provision` interface. Target-side scheduled polling and reviewed selector/branch transitions remain internal. An operator update plan can only follow an already selected, non-divergent branch; it must not silently change the baseline. The public command tree and tests are implemented in [PR #15](https://github.com/benjaminpreiss/themoss.net/pull/15); the actual install/update and recovery behavior is documented in that PR's `packages/cli/src/machine/README.md`.

One plan model can describe different *effects* without granting arbitrary executable steps. A plan is neither authorization nor evidence of a completed change (the receipt serves the latter role). Missing evidence, changed tips, uncertain switch outcomes, a missing install receipt, or a different physical disk all require a stop rather than automatic destructive reconciliation.

This decision does **not** ship issue #1's proposed repair, backup, restore, VM or peer management features. A future web/proxy/VM flow must use signed, authorized, fresh, typed requests to a validating hypervisor management service; the proxy must not run CLI strings on the host or expose a host shell. Existing consumers pinned to older commits retain their original interface until they choose to migrate.
