# CLI guideline findings for `moss machine`

Research notes for the proposed public interface in [ADR 0001](adr/0001-public-machine-cli.md). Sources: [Command Line Interface Guidelines (clig.dev)](https://clig.dev/) and [CLI Style (cli.style)](https://cli.style/). These are design guides, not security specifications; project-specific install invariants remain authoritative.

## Naming and argument shape

- Both guides favour a predictable noun–verb command tree: [clig.dev: Subcommands](https://clig.dev/#subcommands) gives `noun verb` as a common pattern; [CLI Style: Speak in sentences](https://cli.style/#speak-in-sentences) and [Use subcommands, not mode flags](https://cli.style/#structure-over-state) recommend a navigable command hierarchy. **Conclusion:** `moss machine …`, not `moss toolkit …` as a public name and not a flag that silently changes what `deploy` means.
- [clig.dev: Arguments and flags](https://clig.dev/#arguments-and-flags) prefers named flags to several positional arguments; [CLI Style: The target is positional](https://cli.style/#positional-arguments) puts only the subject in the positional slot. **Conclusion:** manifest or SSH target positional; disk, record path and optional values named (`discover root@HOST --disk … --record …`). No positional argument choreography.
- [clig.dev: Subcommands](https://clig.dev/#subcommands) warns against ambiguous similar verbs; [CLI Style: Name the outcome](https://cli.style/#name-the-outcome) argues for names that explain the effect. **Conclusion:** `install` means a new disk install; reserve `update` for an installed machine. Do not publish `deploy` to mean either.

## Plans, preview and confirmation

- [CLI Style: Show the change, not the summary](https://cli.style/#preview-is-a-diff) reserves a meaningful preview for the actual delta. [clig.dev: Interactivity](https://clig.dev/#interactivity) recommends a dry run before a dangerous operation. The current toolkit's `manifest plan` re-probes hardware and verifies the pushed tip, but does **not** calculate a complete disk-layout diff. **Conclusion:** call it `moss machine install plan MANIFEST`, not `install --preview`, until it actually renders the evaluated change. The real operation can simply be `moss machine install MANIFEST`; `install apply` adds a generic verb to an already explicit destructive verb without clarifying its effect.
- [CLI Style: Match confirmation to consequences](https://cli.style/#destruction-is-deliberate) says catastrophic actions require naming the target, never blanket `--yes`; [clig.dev: Arguments and flags](https://clig.dev/#arguments-and-flags) likewise recommends a non-trivial target name or `--confirm=…` for severe loss. **Conclusion:** keep typed whole-disk identity confirmation and re-probe/verify after confirmation. No `--yes` or `--force` to erase a disk. A future non-interactive form would require separately designed reviewed authorization and exact target binding; neither guide overrides issue #14's existing safety contract.
- [CLI Style: Every prompt has a flag equivalent](https://cli.style/#nothing-interactive-only) and [clig.dev: Never require a prompt](https://clig.dev/#arguments-and-flags) generally encourage non-interactive automation, but this conflicts with the current product decision that the destructive install cannot waive typed confirmation. **Explicit exception:** fail closed without a terminal rather than invent a dangerous automation escape hatch. The non-destructive `manifest create` wizard can eventually accept named flags without weakening install.

## Help and future compatibility

- [CLI Style: Make the application self-documenting](https://cli.style/#self-documenting) and [clig.dev: Help](https://clig.dev/#help) favour help at every level, examples, and generated documentation from the command tree. Continue generating JSON and Markdown from argc annotations; add examples at each *public* command. Do not expose private SSH protocol commands merely to fill out public help.
- [CLI Style: Do only what the name promises](https://cli.style/#least-surprise) supports keeping `status`, `plan` and `help` non-destructive. [CLI Style: Exit codes are part of your API](https://cli.style/#exit-codes-are-api) calls for stable machine-consumable outcomes. Define a versioned plan/result format and stable failure codes before promising agent-facing JSON for all operations.
- These references do **not** decide whether an operator should trigger an on-host update. Leave `poll`, remote preparation and selector migration private for now. A public `moss machine update` needs a defined effect and authority before it is offered.
